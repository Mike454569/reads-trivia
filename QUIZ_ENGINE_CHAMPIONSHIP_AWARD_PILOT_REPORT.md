See `CHAMPIONSHIP_AWARD_ENGINE_COVERAGE_REPORT.md` for the full predicate evaluation, including the finding that **no NFL award data exists anywhere in Engine v4** (award tables are CFB-only).

### What is now clearly reusable

Confirmed across all three builds, not just asserted after one:

- **Season-aware team/franchise resolution against `team_aliases`** -- identical `resolve_franchise()` logic, unchanged, used by all three
- **Distractor-pool construction from real Engine-verified alternatives** -- `teams_active_in_season()` for the two team-guessing pilots; a closed-vocabulary sample for the outcome pilot. The *principle* (never fabricate a distractor; always sample from a verified Engine-derived set) held across all three even though the *pool* differs by domain.
- **The overall pipeline shape**: production-safety gate -> deterministic candidate ordering -> per-candidate reject/accept loop with named rejection reasons -> contract validation -> deterministic-JS writer -> funnel-stats JSON -> a *separate* human-review script that rebuilds and asserts byte-for-byte equality against the real output before writing anything
- **The "borrow Engine's own difficulty when Game Factory doesn't cover the domain" pattern** -- used successfully twice now (QB and Championship/Award), both times requiring an exact-match cross-check against the source table rather than trusting the join alone
- **Fixed ID ranges per pilot** (100000s / 200000s / 300000s / 400000s) to make collision impossible without coordination

### What must remain domain-specific

- The actual data-access query and its verification logic (what table, what identity check, what counts as ambiguous) -- this is irreducibly different per domain and was rebuilt from scratch each time after first inspecting what Engine actually has, not assumed
- Question phrasing and the entity being asked about (team-from-player vs. player-from-team vs. outcome-from-team)
- Whether unique-entity enforcement makes sense (yes for Draft/QB, deliberately not for Championship/Award)
- Whether `notes` can be populated at all (depends entirely on what structured facts the source row actually carries)
- The specific rejection-reason taxonomy (each domain surfaced at least one rejection class the others didn't: mid-season trades for QB, historical alias gaps for Draft, none needed for Championship/Award)

### Which validation rules should become shared infrastructure

If a fourth domain is built, these are the pieces worth extracting into a shared module now, since three independent implementations have converged on identical logic:

1. `connect()`/`seeded()` wrapper conventions (already just re-exports of `game_factory`'s own helpers)
2. `resolve_franchise()` and `teams_active_in_season()` -- byte-identical across all three scripts already
3. The contract-validation function (7-key check, difficulty enum check, 4-unique-options check, correctIndex-points-at-verified-answer check) -- identical logic, only the category constant changes
4. The "verify reconstruction against actual persisted output before writing the human-review doc" pattern -- identical structure in all three `generate_human_review*.py` scripts
5. The funnel-stats JSON shape and the deterministic-JS-writer header/footer format

### Does this justify a generic `window.QUIZ_DATA` export framework?

**Partially -- for the scaffolding, not for the domain logic.** Three independent pilots now share, byte-for-byte, roughly the outer half of each script (safety gate shape, contract validation, JS writer, funnel stats, human-review verification pattern) while the inner half (what to query, how to resolve identity, what's ambiguous, where difficulty comes from) has been different every single time and required fresh Engine investigation each time -- Game Factory covered domain 1, was absent for domains 2 and 3 in two different ways (QB had an existing difficulty-only mode to borrow from; Championship/Award did too, coincidentally, but the underlying table shapes and identity risks were unrelated to each other). Extracting the outer half into a shared module (per item 1-5 above) looks safe and worthwhile. Generalizing the inner half into a single configurable framework does not look safe yet -- doing so before a fourth or fifth domain risks baking in assumptions from these three specific cases (e.g. "there's always a `team_aliases`-shaped resolution step") that may not hold for a domain without a team/season axis at all (e.g. a pure player-vs-player stat comparison). Recommend: extract the shared outer-half module now, with byte-identical-output verification against all three existing pilots as a hard gate (per the standing instruction), and defer generalizing the inner half until a domain without a team/season axis has been attempted.
