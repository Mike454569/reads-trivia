## Architectural comparison to the Draft Pilot

### What was shared

No code files are shared between the two exporters (by design, per instruction), but the **pattern** is identical and was reused deliberately:

- `gf.connect()` / `gf.seeded()` -- Engine's own DB handle and deterministic-RNG helpers
- Season-aware team resolution against `team_aliases` (`resolve_franchise()`), verbatim logic
- Distractor-pool construction (`teams_active_in_season()`), verbatim logic -- other real teams active in the same season, never arbitrary names
- The overall shape: production-safety gate -> per-candidate reject/accept loop -> contract validation -> deterministic-JS writer -> funnel-stats JSON -> separate verified-against-actual-output human review script
- The `_audit` side-channel pattern (extra fields carried through generation, stripped before the `.js` write, used only for reporting)

### What had to be domain-specific

- **No Game Factory predicate existed for this domain** -- the Draft Pilot called `game_factory.generate_candidates()`; this pilot queries `qb_team_seasons` directly, since no equivalent QB/season relationship is registered in Game Factory's capability table.
- **Difficulty had no natural source** -- the Draft Pilot got a difficulty score for free from `game_factory`'s internal `_difficulty()` heuristic (recency + rarity). With no Game Factory candidate object, this pilot instead cross-references Engine's own separately-published `qb_season` puzzle mode for a difficulty band, rejecting candidates that don't have one rather than inventing a heuristic.
- **A new identity-consistency check** -- the Draft Pilot's entity was `player_key` from `draft_facts`, which had no observed name inconsistencies. QBs required a new check (`qb_source_id` -> multiple `qb_name` values) that has no Draft Pilot analog, because the underlying source data has real quality issues here that weren't present there.
- **A new "multiple plausible answers" class** -- mid-season trades (same QB, same season, two teams) have no equivalent in `draft_facts` (a player is drafted exactly once) and required a dedicated exclusion rule.
- **Question phrasing and entity roles differ** -- "guess the team" here vs. the Draft Pilot's same shape but different underlying relationship; notes are populated here (source-backed facts were constructible) vs. always empty in the Draft Pilot (no explanation field existed on that payload).

## Reusability assessment for additional trivia families

The exporter *shape* generalized cleanly on the first attempt at a second, materially different domain: production-safety gate, deterministic candidate ordering, a per-candidate reject/accept loop with named rejection reasons, contract validation, a verified-against-actual-output human-review generator, and a funnel-stats JSON consumable by a reporting step. None of that had to change conceptually for QB/season data. What *does* need to be rebuilt for each new domain is the actual data-access and verification logic in the middle -- which tables to trust, how to resolve identity, what counts as an unambiguous answer, and where a genuine Engine-computed difficulty signal can be found (or honestly can't). A future third domain would likely benefit from factoring the *shared* pieces (season-aware team resolution, distractor-pool construction, the contract-validation/human-review/audit-report scaffolding) into a small shared helper module -- but that refactor should only happen with explicit approval and a byte-identical-output verification step for both existing pilots, exactly as this task's instructions require.
